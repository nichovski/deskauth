# Deskauth - desktop TOTP authenticator

**Date:** 2026-11-03 · **PR:** https://github.com/nichovski/deskauth/pull/1 · **Author:** Bogdan

## What it does

A desktop app (Linux, Windows, macOS) that shows TOTP codes, so 2FA codes can be read without the phone.

- First run: set a master password. Every start after that asks for it.
- Import accounts from Google Authenticator: on the phone, Transfer accounts > Export, then scan the QR with the laptop camera (or load an image). Exports split over several QR codes are collected until all batches are in, then merged once.
- Re-import any time. Accounts with a secret already in the vault are skipped.
- Add one account from an `otpauth://` QR or by typing the secret.
- List with search, Enter copies the top match, click copies a row. The clipboard is cleared after 30 seconds if it still holds that code.
- Auto-lock after 5 minutes of no input.
- Rename, delete, change password, and "Delete vault and start over" when the file is damaged.
- On Omarchy the colors follow the current theme and change live.

## Why

Taking out the phone for every 2FA prompt was the annoyance. Key decisions:

- **No live sync with the phone.** Google Authenticator has no API and its cloud backup is private. The export QR is the only way out, so "sync" means import plus re-import that merges.
- **Camera is the main import path.** Android blocks screenshots of the export screen, so an image import alone would not work for Android users.
- **Each computer imports on its own.** Nothing leaves the machine. No network code at all.
- **Tauri 2.** Small native apps on all three OSes, and secrets stay in Rust; the webview only ever gets labels, codes and counts.
- **Public repo, unsigned builds.** Built for personal use. Others build and sign it themselves (README explains how).
- **No password recovery.** Forgetting the password means deleting the vault and importing again; the phone stays the backup.

## How it works

Rust modules in `src-tauri/src/`, each with in-file tests, and only `commands.rs` and `lib.rs` know about Tauri:

- `account.rs` - account model. The secret is redacted in `Debug` and zeroized on drop; `validate()` guards digits (6/8), period and base32.
- `totp.rs` - RFC 6238 (SHA1/256/512), tested against the RFC vectors.
- `migration.rs` - decodes `otpauth-migration://` (Google's protobuf, structs written by hand with prost derive, no protoc) and `otpauth://`. HOTP and MD5 entries are skipped and counted. Handles a raw `+` turned into a space and `Issuer:name` prefixes.
- `import.rs` - import session: tracks batch id/index/size, ignores repeats, dedupes identical QR content.
- `merge.rs` - duplicate means equal secret bytes, even with a different name.
- `vault.rs` - `vault.json` in the app data dir. Argon2id (64 MiB, t=3, p=1) and XChaCha20-Poly1305, header as AAD, fresh nonce per save, temp file at 0600 then rename. Non-default KDF params are rejected before the KDF runs, so a hostile file cannot force huge memory use. Wrong password and damaged file are separate errors.
- `qr.rs`, `camera.rs` - QR decoding with rxing (ZXing port; rqrr was dropped because it missed dense export QR codes at some image sizes); camera via nokhwa on its own thread, frames downscaled to 1280 px before decoding, a small JPEG preview for aiming.
- `theme.rs` - reads `~/.local/state/omarchy/current/theme/colors.toml` and watches `current/` (Omarchy swaps the `theme` directory there on switch), debounced 200 ms.
- `commands.rs` - app state and commands. No code path takes one mutex while holding another. Auto-lock checks both a monotonic clock and the wall clock, so time asleep counts.

UI in `src/` is plain TypeScript, no framework. Rows are keyed by account id and updated in place each second, so clicks are not lost to the redraw. All user and QR text goes in through `textContent`.

## Unlock methods (2026-11-05)

**What.** Besides the password, the vault can open with a YubiKey or a fingerprint. Settings > Unlock methods picks one of three modes: `password` (password only), `any` (password, any registered YubiKey, or the fingerprint), `password_yubikey` (password and a YubiKey touch together, nothing else). In `any` mode the unlock screen listens by itself while its window is focused and visible (on blur it cancels the scan and stops polling, so fprintd's single reader claim and the key are free for sudo, the screen locker and the browser): it starts a fingerprint scan when it shows (restarted after a no-match or timeout on Linux) and polls every 2 s for a plugged-in YubiKey (`yubikey_present`, device list only), then asks it for a touch. On Windows the key keeps a "Use YubiKey" button, and Touch ID / Windows Hello are not restarted on their own. In `password_yubikey` mode the password submit asks for a touch.

**Why.** Typing the master password many times a day was the next annoyance after the phone. The password stays the recovery path in `password` and `any`; `password_yubikey` is for people who want a real second factor and accept that losing every key loses the vault (Settings warns when only one key is registered).

**How.**

- `vault.rs` - file format v2. Accounts are encrypted under a random vault key; key slots (`password`, `yubikey`, `fingerprint`, `password_yubikey`) wrap that key under their own KEK, with kind and id in the AAD. v1 files upgrade on the next password unlock. Switching into or out of `password_yubikey` makes a fresh vault key. No device code here; it takes passwords, hmac outputs and fingerprint secrets as bytes.
- `unlock/` - two traits, `HmacKey` (FIDO2 `hmac-secret`, touch only, rp id `deskauth`) and `Fingerprint`, with one file per platform: `fido_hid.rs` (Linux, macOS), `fido_windows.rs` (webauthn.dll), `finger_linux.rs` (fprintd verify, then the secret from the Secret Service keyring), `finger_macos.rs` (Keychain item behind Touch ID), `finger_windows.rs` (Windows Hello signature). Tests use fakes.
- `unlock_commands.rs` - the commands as plain functions over `&AppState`. Each change holds the ops lock (`commands::begin`) for its whole run, so two vault changes cannot interleave, and takes the vault mutex only for quick reads and the final change, never during a touch, a scan or Argon2. Unlocks only read the file and skip the ops lock (except the v1 upgrade), so password, fingerprint and YubiKey attempts run side by side: the first to finish wins, a later one is dropped, and any unlock cancels a running fingerprint scan (`AppState::finger_cancel`, also set by `unlock_cancel`). Events: `touch-needed { name }` lets the UI say "Touch Blue key"; `finger-status { state, message }` drives the fingerprint icon (`scanning`, `retry` with a hint, `no_match`).
- YubiKey PIN: only `makeCredential` at registration carries it (`yubikey_add` / `set_mode` take an optional `pin`, held in `Zeroizing`); every assertion stays touch only, so the `hmac-secret` output (computed without user verification) is the same at registration and unlock.
- UI: `src/views/unlock.ts` and the "Unlock methods" card in `src/views/settings.ts`. Device names go in through `textContent`.
- Limits: on Linux the fingerprint is convenience (any program running as you can read the keyring item); macOS needs a signed build; Windows YubiKey needs WebAuthn API v4. macOS and Windows are compiled in CI but untested on hardware. Removing a lost key does not protect old copies of `vault.json`.
